# Agentic Search UX Overhaul - Technical Analysis & Implementation Plan

## 1. Real-Time Sync Architecture

Currently, the `agenticSearchWorker` operates asynchronously as a Cloud Task without persisting its granular execution state to Firestore, meaning the frontend has no mechanism to track its progress.

To enable a **Real-time Progress Radar**, we need an event-driven architecture using Firestore as a state synchronization layer:

1. **Job Initialization (`triggerAgenticSearch`)**: When the user clicks "Start Search" in the UI, the Callable function must create a document in a new `agentic_search_jobs` Firestore collection with an initial state (`status: 'queued'`) and pass the newly created `jobId` to the `agenticSearchWorker` payload.
2. **State Updates (`agenticSearchWorker`)**: As the background worker advances, it will update the job document in Firestore to reflect its current phase:
   - `generating_queries` (Genkit prompt to generate 3 queries)
   - `scraping_web` (Brave Search API calls and full HTML fetching)
   - `scoring_triage` (Genkit heuristic pre-filtering and triage)
3. **Frontend Sync**: The React frontend (e.g., within `OscProfileView`) will use Firebase `onSnapshot` to listen to the `agentic_search_jobs` collection where `oscId == currentOscId`. This stream will directly drive the Progress Radar UI components.
4. **Debounced Writes**: To prevent hitting Firestore's soft limit of 1 write/sec per document and optimize costs, the worker should batch numerical progress updates (e.g., `linksProcessed`, `editaisFound`) and commit them after each search query loop, rather than per link.

## 2. Data Schema Updates

### New Collection: `agentic_search_jobs`
To support granular progress tracking, we need to introduce a new top-level collection.
```typescript
{
  id: string; // Document ID
  oscId: string; // Indexed for querying
  status: 'queued' | 'generating_queries' | 'scraping_web' | 'scoring_triage' | 'completed' | 'failed';
  progress: {
    queriesGenerated: number;
    linksFound: number;
    linksEvaluated: number;
    validEditaisEnqueued: number;
  };
  logs: string[]; // Minimal string logs for the Radar UI (e.g., "Buscando: 'editais cultura SP'")
  startedAt: Timestamp;
  updatedAt: Timestamp;
  completedAt?: Timestamp;
  error?: string;
}
```

### Schema Additions for Smart Insight Cards
The requested **Smart Insight Cards** require an "AI Summary" and badges. We will update the existing `matchSchema` (in `functions/src/shared/schemas.ts`) and the `scoreMatch` Genkit flow.
- Add `aiSummary`: A concise 1-2 sentence synthesis of the match (distinct from the lengthy, analytical `reasoning` field).
- Add `badges`: An array of tags (e.g., `['Alto Alinhamento', 'Prazo Curto', 'Regional']`) generated by the LLM during scoring.
- The `matches` Firestore documents will automatically inherit these fields to be displayed in the UI.

## 3. Production Risks & Edge Cases

### A. Silent Task Failures (The "Zombie" Loading State)
**Risk:** Cloud Functions v2 (Cloud Tasks) can fail silently due to OOM (Out of Memory) errors, unhandled exceptions in Genkit, or hitting the 540-second timeout. If the worker crashes, the `agentic_search_jobs` document remains stuck in a `scraping_web` state indefinitely, causing the frontend to spin forever.
**Mitigation:**
- **Frontend Stale Check:** The React UI must monitor the `updatedAt` timestamp. If a job is not `completed` or `failed` and hasn't been updated in over 10 minutes, the UI should gracefully degrade to a "Timeout/Failure" state, allowing the user to retry.
- **Backend Try/Catch:** Wrap the entire worker payload in a `try...catch` block to explicitly update the job status to `failed` and save the error message before the function exits.

### B. Firestore Read/Cost Implications
**Risk:** A real-time progress tracker can inadvertently cause excessive read/write billing. If the frontend uses unbounded `onSnapshot` queries, or the backend writes every single scraped URL to Firestore, it will bloat costs.
**Mitigation:**
- The backend must only update the job document at significant milestones (e.g., once per query completed, or using a debounced update function every 5 seconds).
- The frontend must filter the listener (`where('oscId', '==', oscId)` combined with `orderBy('createdAt', 'desc')`, limited to `1`), and ideally detach the listener once the job reaches `completed` or `failed`.

### C. Rate Limits & Thundering Herds
**Risk:** The Brave API and Vertex AI have strict rate limits. Spamming the "Search" button could exhaust these limits and enqueue too many overlapping extraction workers.
**Mitigation:**
- Disable the "Start Search" button in the UI if an active job (`status` not completed/failed) already exists for that OSC.
- Maintain the `maxConcurrentDispatches: 2` limit on the `agenticSearchWorker` queue.

## 4. Step-by-Step Execution Plan

**Phase 1: Backend Scaffolding & State Tracking**
- Define the TS interface for `agentic_search_jobs`.
- Modify `triggerAgenticSearch` to create the initial job document and inject `jobId` into the task payload.
- Update `agenticSearchWorker` to accept `jobId`, update the Firestore document at key milestones (generating queries, fetching links), and handle global exceptions to set the `failed` state.

**Phase 2: Frontend Progress Radar**
- Create a `useAgenticSearchTracker(oscId)` React hook that subscribes to the latest active job via `onSnapshot`.
- Implement the Stale/Zombie timeout logic within the hook (falling back to a failed state).
- Build the Progress Radar UI component with 5 distinct states: Idle, Generating, Scraping, Scoring, and Done/Error.

**Phase 3: Smart Insights & AI Summaries**
- Extend `matchSchema` in `shared/schemas.ts` to include `aiSummary` (z.string) and `badges` (z.array(z.string)).
- Update the `scoreMatch` LLM prompt to instruct the AI to generate a punchy 2-sentence summary and 2-3 relevant tags/badges.
- Update the Match Card UI (e.g., `NgoMatchView`) to render these new fields if they exist (ensuring backward compatibility for old matches).

**Phase 4: Empty & Failure States (UX Polish)**
- Implement a graceful "No Editais Found" empty state in the Radar UI (e.g., if `validEditaisEnqueued === 0` at completion).
- Implement explicit error states with actionable retry buttons if the backend aborts or the Brave API fails.
